# AI 浏览器自动化测试 Agent MVP 方案

## 1. 总体方案

本项目交付一个供其他团队使用的 AI 测试 Agent 流水线。它以已有测试用例为输入，通过 Browser Agent 执行可见页面上的正流程测试，保存结论和证据，再把异常与无法判断的内容交给人工。

AI 用于提高人工测试效率，不替代人工最终验收。当前阶段优先验证可行性和正流程闭环，不追求完整测试平台。

## 2. MVP 边界

### 包含

- 读取已有、只读的测试用例；
- 默认尝试执行全部输入用例，不做前置能力分类；
- 使用 Cursor Agent 原生 Browser 操作和观察页面；
- 对每条用例记录状态、执行过程、原因和证据；
- 生成需要人工处理的用例清单；
- 首版以 Cursor Skill、模板和提示词交付。
- 通过 GitHub Skill 仓库分发，并随包提供 Windows/Linux x64 的静态结果写入器；

### 不包含

- 独立的 Playwright 测试阶段；
- 读取或修改待测项目代码；
- 调用内部 API 或访问数据库；
- 自动修复测试发现的问题；
- 自动改写来源用例；
- 视觉体验、真实设备、CAPTCHA 等必须人工判断的能力；
- 多平台 Agent、常驻服务和完整测试管理 UI。
- Go、Python、Node.js、npm、Playwright 或额外 Browser MCP 运行时安装依赖；
- 覆盖全部状态、证据和业务语义的独立确定性校验程序。
- 首版 Cursor Marketplace Plugin 和无人值守自动更新。

## 3. 执行流程

```text
测试人员提供运行配置和只读用例
  ↓
解析 mode、Skill 版本和 Schema 版本
  ↓
Browser Preflight
  ↓
主 Agent 顺序读取并调度每条用例
  ↓
Skill 内部调用 Cursor Browser 观察页面、执行步骤、检查预期
  ↓
每条用例完成后追加执行记录、过程事件并更新状态
  ↓
生成批次汇总和人工处理清单
```

用例假设彼此独立。MVP 可以复用相同账号的登录会话，但不得让前一条用例产生的业务数据成为后一条用例的隐式前置条件。

## 4. 判定规则

| 内部值 | 中文展示 | 含义 |
|---|---|---|
| `pending` | 待测试 | 尚未开始执行 |
| `passed` | 已通过 | 所有步骤执行完成，且每个预期都从可见页面直接观察到 |
| `failed` | 不通过 | 已观察到与预期相矛盾的页面行为 |
| `blocked` | 测试受阻 | 因 Browser、环境、登录、权限或前置数据而无法执行 |
| `inconclusive` | 无法判断 | 已执行，但可见页面不足以支持通过或不通过 |
| `retest_pending` | 待复测 | 修复或环境变化后等待重新执行 |

点击成功、页面没有报错或 Agent 走完步骤，都不能单独作为通过依据。`blocked` 和 `inconclusive` 不得转换为 `passed`。

默认把 `failed`、`blocked` 和 `inconclusive` 放入人工处理清单；测试人员可以在结果出来后增加人工测试范围。

## 5. 数据模型

MVP 保持三类表，不额外建立数据库实体：

| 数据 | 写入规则 | 最少内容 |
|---|---|---|
| 用例 `test_case` | 只读 | ID、标题、账号、前置条件、步骤、逐步预期 |
| 用例状态 `case_status` | 可更新 | 中文表头、用例 ID、中文 Browser 状态、中文人工处理/清理状态、最后执行时间、最后记录 ID |
| 执行记录 `case_execution` | 只追加 | execution_id、run_id、用例 ID、尝试次数、起止时间、结论、步骤观察、原因、证据、副作用与清理状态 |

批次的环境、Cursor 版本、开始时间和用例集版本可以保存在结果目录的 manifest/summary 中。若后期需要数据库查询，再将批次提升为独立实体。

## 6. 输入

### 测试用例

每条用例至少包含：

- 唯一 ID；
- 标题；
- 使用的账号标识；
- 前置条件；
- 有序步骤；
- 每一步的可观察预期。

### 运行配置

测试人员只提供必要信息：目标 URL、测试账号、禁止操作和必要备注。AI 在不改变业务语义的前提下自行处理滚动、等待、关闭无害提示和切换标签页等 UI 细节。

普通账号支持用户名/密码。短信 mock 账号使用“浏览器自动填入”标记：Agent 输入手机号并点击获取验证码，然后等待页面自动填写。

### 来源适配

首版支持 Markdown/结构化文本以跑通闭环。Excel 随后加入。飞书文档由外部飞书 Skill/CLI 完成下载和交互，本项目只消费其提供的本地结构化内容。

## 7. 证据与审计

每条执行记录至少包含：

- 实际执行步骤；
- 每一步观察到的页面结果；
- 最终 URL 或页面标题；
- 起止时间；
- 最终状态；
- 异常步骤和原因；
- 可用的截图引用。

每次运行额外保存 `run-events.jsonl`。正常模式记录恢复和审计所需的关键事件，只在异常用例或 Preflight 失败时截图；开发模式增加与来源步骤一一对应的步骤观察、脱敏后的 Browser action 前后事件、UI 适应、截图和关键写入前后事件，并为每条实际执行用例截图。运行模式只影响日志详细度，不改变测试行为与结论。

正式执行前按输入校验、Browser 能力、目标导航、应用识别完成分阶段前置检查（Preflight）。阶段失败时记录事实、带置信度的推断和建议；不得因页面为 503 就断言环境故障或要求等待恢复。目标 URL 改变时必须新建 run。

写操作必须记录测试数据副作用。固定值出现冲突时不得擅自改写或把历史数据当作本次创建结果；只有明确允许自由取值时才能生成唯一数据。没有来源清理步骤时，创建数据进入独立的测试数据清理清单，不自动删除。

状态表是当前快照，执行记录是历史事实。复测只能追加新记录，再更新状态表，不能修改旧记录。

每次追加前必须检查 execution ID 和“用例 ID + attempt”唯一。无法安全修复的历史冲突使整次运行无效：保留原始结果，记录 `self_check=failed`、`run_valid=false`，再使用新 run ID 重跑。

## 8. 交付与演进

### MVP

- Cursor Agent 3.15.x Agent Window；
- Skill 内部调用 Cursor 原生 Browser；
- Skill + 提示词 + 输入/结果模板；
- 文件形式的状态、执行记录、过程事件和汇总；
- 随 Skill 交付跨平台编译型 JSONL 写入器；使用者无需安装语言运行时；
- 结束前由 CLI 校验 JSONL，再由 Agent 完成跨文件一致性自检。
- Cursor 官方 GitHub Skill 导入作为安装主入口；
- GitHub Actions 自动测试、交叉编译并按 tag 发布 Release；
- 安装后校验 Skill 可发现、文件完整以及 CLI 与 Skill 版本一致。

### 后续

- Excel 适配；
- 多账号调度优化；
- 飞书适配；
- 其他 Browser Provider；
- 代码与数据库只读上下文；
- 独立的完整编排 CLI/服务和插件 UI。
- macOS/ARM64 支持、Cursor/Agent Plugin 与 Marketplace 一键安装、团队更新。
- 覆盖跨文件状态、证据和业务语义的完整确定性校验器。

分发侧已经补充 Windows/Linux x64 构建、交付校验、GitHub tag Release 和 Cursor 安装验收，仍需在 Cursor 中实际执行一次 GitHub Remote Rule 导入回归。分发设计见[构建、分发与安装设计](distribution.md)。
